System Architecture Diagram

The i@masjid Mosque Management System is designed using a 3-Tier Architecture consisting of a Presentation Layer (Frontend Web Client), an Interface & Application Logic Layer (Javascript Coordinators & Gateways), and a Database Storage Layer (Supabase Cloud PostgreSQL Engine & Row Level Security).

Table 7: korban_campaigns Stores Qurban/Korban animal sacrifice campaigns created by the mosque for a specific year.
No.Field Name Data TypeKey Constraint / DefaultDescription
1idSERIALPKNOT NULLAUTO INCREMENTAuto-incrementing unique identifier for each Korban campaign record
2mosque_idUUIDFKNULLABLEReferences mosques.id. Links the campaign to the mosque managing the sacrifice.
3yearINTEGER—NOT NULLThe Hijri or Gregorian year of the Korban campaign (e.g., 2026). Used to organise campaigns annually.
4animal_typeTEXT—NOT NULLType of sacrificial animal for the campaign. Values: 'Lembu (Cow)' (7 parts) or 'Kambing (Goat)' (1 part)
5price_per_partNUMERIC(10,2)—NOT NULLCost per participation share in MYR (e.g., 750.00 for Cow, 950.00 for Goat). Displayed in the Korban form.
6total_partsINTEGER—NOT NULLTotal number of available participation slots/shares for this campaign (e.g., 35 for Cow, 10 for Goat)
7created_atTIMESTAMPTZ—DEFAULT now()Timestamp of when the Korban campaign was created in the system by the admin
Table 8: korban_participants Stores individual Qurban participant registrations, payment status, and installment plan details.
No.Field Name Data TypeKey Constraint / DefaultDescription
1idUUIDPKDEFAULT uuid_generate_v4()NOT NULLUnique auto-generated identifier for each participant registration record
2campaign_idINTEGERFKON DELETE CASCADEReferences korban_campaigns.id. Links participant to the campaign. Deleted if campaign is removed.
3nameTEXT—NOT NULLFull name of the Korban participant as entered in the registration form
4phone_numberTEXT—NOT NULLContact phone number of the participant for admin communication and receipt purposes
5parts_qtyINTEGER—NOT NULLNumber of participation shares the user has registered for (1 share minimum; up to available total_parts)
6payment_statusTEXT—DEFAULT 'pending'Current status of the payment lifecycle. Values: pending (awaiting admin approval), paid (approved by admin), rejected (rejected by admin), cancelled (cancelled by user)
7payment_methodTEXT—DEFAULT 'full'Payment plan selected by the participant. Values: full (single full payment), installment_3 (3-month plan, no extra charge), installment_6 (6-month plan, +1.5% charge fee applies)
8installment_monthsINTEGER—NULLABLENumber of installment months selected. Value is 3 (3-month plan), 6 (6-month plan), or NULL (full payment)
9charge_feeNUMERIC(10,2)—DEFAULT 0.00Additional service charge in MYR applied for the 6-month installment plan (calculated as 1.5% of total amount). Zero for full payment and 3-month plan.
10registered_atTIMESTAMPTZ—DEFAULT now()Timestamp of when the participant submitted the Korban registration form

Presentation Slides (Ready for Screenshot)

1. Introduction

i@masjid (Mosque Management System) is a centralized web-based platform designed to digitalize daily mosque administration.

  • Transitions traditional manual operations into a seamless digital ecosystem.
  • Targets core administrative burdens: Tabung Collections, Event Registrations, and Qurban Campaigns.
  • Empowers mosque administrators (AJK) with real-time data and tracking capabilities.
  • Provides the local Muslim community (Kariah) with accessible, transparent digital interaction.
Slide 1

2. Problem Statements

  • Manual Data Loss: Paper-based tracking of participant quotas and donations leads to data redundancy and human errors.
  • Payment Inefficiencies: Manual bank transfer verification requires heavy administrative workload and delays confirmation.
  • Communication Gap: Lack of a centralized platform for the local Kariah to receive instant mosque announcements and event updates.
Result Survey Analysis: Over 85% of mosque administrators reported difficulty in tracking manual receipts and managing large-scale events like Qurban.

3. Objectives

To overcome the identified problems, the objectives of this project are:

  • To Develop: A centralized Mosque Management System (i@masjid) for structured and efficient administration.
  • To Integrate: An automated payment gateway (ToyyibPay) to process secure online Tabung donations and Qurban registrations.
  • To Provide: Real-time analytical dashboards for administrators to monitor campaign progress, generate reports, and track community engagement.

4. Project Scopes

  • Target Audience: Mosque Administrators (AJK) and Mosque Community Members (Kariah).
  • System Modules:
    • User Authentication & Profiling
    • Event Management & Announcements
    • Tabung E-Donation System
    • Qurban Campaign Management & Quota Tracking
  • Technology Stack:
    • Frontend: HTML, CSS, JavaScript (Vanilla Web Technologies)
    • Backend: Supabase PostgreSQL (Cloud Database-as-a-Service)
    • API: ToyyibPay Simulated Environment

6. Methodology

This project implements the Agile Software Development Life Cycle (SDLC) to ensure flexibility and iterative refinement.

  • Phase 1 (Planning & Requirements): Elicitation of mosque operational pain points.
  • Phase 2 (Design): ERD formulation, Architecture mapping, UI wireframes.
  • Phase 3 (Development): Supabase backend initialization, Gateway integration.
  • Phase 4 (Testing): Unit testing of Qurban limits, ToyyibPay status simulation.
  • Phase 5 (Deployment): Cloud hosting and final evaluation.
Slide 7

7. Architecture Design

The system utilizes a modern 3-Tier Cloud Architecture:

  • Client Tier: Web Browser executing native JavaScript.
  • Application/Coordination Tier: JS API Coordinators managing ToyyibPay callbacks and Supabase fetch logic.
  • Data Tier: Supabase PostgreSQL Database with active Row Level Security (RLS) ensuring strict access controls.
